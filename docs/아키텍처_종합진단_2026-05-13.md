## 1. 한 줄 총평

문서와 데모 UI는 많이 쌓였지만, 핵심 예측 신뢰도·하드웨어 실측·배포 재현성·비밀관리·테스트 체계가 약해서 현재는 "운영 시스템"보다는 "시연용 통합 프로토타입"에 가깝다.

## 2. 프로젝트가 하는 일

BUSTAGO는 버스 정류장 혼잡도를 예측해 학생에게 탑승 판단과 노선 추천을 제공하고, 운영자에게 실시간 카운팅·통계 대시보드를 제공하려는 시스템이다.

확인된 주요 기능:

| 영역 | 기능 |
| --- | --- |
| 학생 PWA | 정류장 선택, 현재 혼잡도, 6시간 예측, 노선별 추천, 광주 BIS 도착정보 표시 |
| 운영자 대시보드 | 혼잡도 차트, 지도, 통계표, Jetson 카운팅 상태 표시 |
| Backend API | `/api/predict`, `/api/stations`, `/api/stats`, `/api/crowd-count`, `/api/route-recommend`, 광주 BIS 프록시 |
| ML | 서울시 승하차·기상·혼잡도 데이터를 기반으로 RandomForest 모델 학습 및 예측 |
| Hardware | Jetson Orin Nano + YOLOv8 + DeepSORT + Line Crossing 기반 대기/탑승 인원 카운팅 |

## 5. 좋은 점

1. 기능 단위 디렉터리 분리가 명확하다. `backend`, `frontend`, `ml`, `hardware`, `docs`가 목적별로 나뉘어 있다.
2. Flask는 app factory와 Blueprint 구조를 사용한다. 작은 프로젝트 기준으로는 확장 출발점이 있다.
3. 학생 PWA와 Admin 대시보드가 실제 화면 단위로 구현되어 있다.
4. ML 모델 파일과 학습 데이터가 로컬에는 존재하고, 추론 인터페이스도 분리되어 있다.
5. 입력 검증, rate limit, 캐시, SQLite fallback 같은 실용적 장치가 일부 들어가 있다.
6. 하드웨어 연동 방향이 코드와 문서에 모두 존재한다. 단순 아이디어 문서만 있는 상태는 아니다.
7. `CONTRIBUTING.md`에 AI 산출물 검토 원칙과 추정/사실 구분 규칙이 있는 점은 좋다.

## 6. 걱정되는 점

### 6.1 보안/비밀관리

- `backend/config.py`에 광주 BIS API 키 기본값이 하드코딩되어 있다. 이 문서에는 값을 적지 않는다. 실제 키라면 즉시 회전 대상이다.
- `frontend/student/app.js`, `frontend/admin/dashboard.js`에는 API 응답을 `innerHTML`로 조립하는 부분이 있다. 외부 API 또는 프록시 데이터가 섞이면 XSS 위험이 생길 수 있다.
- `/api/crowd-count`는 인증 없이 카운팅 데이터를 받는다. 같은 네트워크에서 임의 수치 주입이 가능하다.

### 6.2 설정/배포 재현성

- `.env.example`은 `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`를 안내하지만 실제 `backend/config.py`는 `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DB`, `MYSQL_USER`, `MYSQL_PASSWORD`를 읽는다. 문서대로 설정해도 MySQL 설정이 적용되지 않는다.
- `docker-compose.yml`의 backend healthcheck는 `curl`을 사용하지만 `backend/Dockerfile`은 curl을 설치하지 않는다.
- `rf_model.pkl`과 `data/`는 로컬에는 있지만 `.gitignore` 대상이다. 새 clone이나 CI 환경에서 동일하게 재현된다고 보기 어렵다.

### 6.3 데이터/DB 품질

- `backend/schema.sql`의 `routes` 테이블은 seed 중복을 막을 unique 제약이 없다. 실제 SQLite에서 route seed 중복이 확인됐다.
- `INSERT OR IGNORE`는 unique/primary key 충돌이 있을 때만 의미가 있는데, 현재 route seed는 자동 증가 `id` 외 자연키 제약이 없어 중복 삽입될 수 있다.
- `backend/models/db.py`는 MySQL 우선, 실패 시 SQLite fallback 방식이다. 개발 편의성은 좋지만 운영에서 DB 장애를 조용히 SQLite로 우회하면 데이터 일관성 문제가 생길 수 있다.

### 6.4 Backend 코드 품질

- `backend/routes/recommend.py`는 DB helper가 dict를 반환하는데 tuple 인덱싱을 사용한다. 정적 route가 아닌 DB fallback 경로에서 깨질 가능성이 크다.
- `backend/routes/predict.py`는 모델 파일이 없으면 조용히 더미 예측으로 fallback한다. 시연에는 편하지만 운영에서는 장애를 숨긴다.
- 여러 곳에 broad `except Exception`과 조용한 fallback이 있다. 실패를 숨기기 때문에 관측 가능성이 낮다.

### 6.5 ML 신뢰도

- 문서상 CV 0.9962가 표시되어 있지만, 이 수치를 현장 예측 신뢰도로 받아들이기는 어렵다.
- 라벨은 서울 승차량 분위수 기반이고, 요일은 placeholder이며, 실제 예측 API는 날씨·이전 승하차를 대부분 기본값으로 넣는다.
- 서울 데이터로 학습한 모델을 광주 정류장에 직접 적용하는 것은 도메인 이동 문제다. 광주 실측 검증 없이는 성능 주장을 강하게 할 수 없다.

### 6.6 테스트/검증

- 시스템 Python에서 `python3 -m pytest`는 `No module named pytest`로 실패했다.
- `.venv`에서는 제한된 ML mock 테스트만 통과했다.
- `ml/data_collection/test_api.py`, `ml/data_collection/test_api_v2.py`는 이름은 test지만 import 시점에 실제 외부 API를 호출한다. 전체 pytest 대상으로 안전하지 않다.
- CI 설정은 확인되지 않았다.

### 6.7 하드웨어/운영 리스크

- `docs/STATUS_2026-05-13.md` 기준 HW 부품 미수령이 계속 블로커다.
- Jetson 카운팅 스크립트는 구현되어 있지만 실제 카메라, TensorRT, 현장 각도, 조명, 이동 동선에서 검증된 결과는 확인하지 못했다.
- 시연 계획서에는 성공 기준이 있지만, AI 카운팅 정확도 리포트는 HW 도착 후 채워야 하는 상태다.

## 7. 완성도 판단

**MVP 직전**

화면, API, ML, 하드웨어 코드가 모두 "형태"는 갖췄다. 하지만 실제 MVP라고 부르려면 최소한 재현 가능한 실행, 더미 fallback 없는 예측, 하드웨어 실측, 테스트 자동화, 비밀관리, Docker 기동 검증이 필요하다.

현재 상태는 발표/시연용으로는 꽤 가까우나, 실제 사용자를 태우는 MVP로는 아직 위험하다.

## 9. 내가 이 프로젝트를 맡는다면

1. 먼저 "시연 가능한 것"과 "운영 가능한 것"을 분리한 상태표를 다시 쓴다.
2. 비밀관리, env 변수명, DB seed 중복, 추천 API 버그를 하루 안에 P0로 고친다.
3. backend/ML 테스트를 임시 DB와 mock 네트워크 기반으로 재구성하고 CI를 붙인다.
4. ML 모델의 데이터 계보와 성능 수치를 다시 검증한다. CV 0.9962는 그대로 믿지 않는다.
5. HW가 없을 경우의 demo mode를 명시적으로 만들고, HW 도착 즉시 카운팅 정확도 리포트를 채운다.

## 12. 사실과 추정 구분

### 확인한 사실

- `backend`, `frontend`, `ml`, `hardware`, `docs` 구조가 존재한다.
- Flask app factory와 Blueprint 기반 API가 존재한다.
- 학생 PWA와 Admin 대시보드 코드가 존재한다.
- RandomForest 모델 추론 코드와 로컬 모델 파일이 존재한다.
- `hardware/counter.py`에 YOLOv8 + DeepSORT + Line Crossing 카운팅 루프가 존재한다.
- 제한된 ML mock 테스트는 `.venv`에서 통과했다.
- `docs/STATUS_2026-05-13.md` 기준 HW 부품 미수령이 리스크로 명시되어 있다.

### 추정 또는 판단

- "운영 가능"이 아니라 "MVP 직전"이라는 평가는 코드 구조, 테스트 상태, 배포 재현성, HW 미검증 상태를 종합한 판단이다.
- ML 성능 수치가 현장 신뢰도를 보장하지 않는다는 평가는 데이터 생성 방식과 운영 feature 입력 방식을 근거로 한 아키텍처적 판단이다.
- frontend `innerHTML` 사용은 실제 공격 가능성이 확인된 취약점이라기보다, 외부 데이터가 섞일 때 위험해질 수 있는 코드 패턴이다.

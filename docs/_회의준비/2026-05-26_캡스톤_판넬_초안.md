## 1. 작품개요 및 필요성

### 작품 개요

BUSTAGO는 광주대학교 인성관 셔틀 정류장과 정문 시내버스 정류장에서 **버스 정류장 대기 혼잡도와 차내 만차 가능성을 결합 예측**하여 학생의 탑승 의사결정을 지원하는 AI 기반 모바일·웹 시스템이다.
서울시 공공데이터포털의 차내 혼잡도·승하차 이력 데이터로 학습한 RandomForest 모델을 광주 환경에 직접 적용(Transfer)하고, 정류장 현장에는 Jetson Orin Nano + YOLOv11 + DeepSORT 기반 1대 카메라를 설치하여 실시간 대기 인원을 카운팅한다 (Jetson Orin Nano TensorRT FP16 YOLO 단독 38.5 FPS, 풀 파이프라인 ~14 FPS).

### 필요성

- **학생 측 문제**: 등하교 피크 시간(8~9시·17~18시)에 셔틀·시내버스가 만차로 탑승 실패 → 지각·장시간 대기. 현재 학생은 "정류장에 가봐야 만차인지 안다."
- **운영자 측 문제**: 광주대학교 셔틀 6호차 운영 시 어느 시간대에 증차해야 할지 정량 지표가 없다 → 경험·민원 기반 의사결정.
- **데이터 측 한계**: 광주 BIS API는 도착 정보만 제공하고 차내 혼잡도는 없다. 광주시 자체 학습 데이터도 절대 부족.
- **본 작품의 해법**: 서울시 공공데이터(차내 혼잡도 포함) 학습 모델 → 광주 정류장 이식 + Jetson 1대 카메라로 정류장 대기 인원 실측 → **두 신호를 결합하여 탑승 가능성을 예측**.

### 차별점 (관련 사례 대비)

| 사례 | 한계 | BUSTAGO 차별점 |
|------|------|---------------|
| 뻐정 (광주 버스 혼잡도 예측) | SSD + 추적 부재, 정류장 외부 시점 부족 | YOLOv11 + DeepSORT 트래킹으로 중복 카운팅 방지 |
| 부산대 캡스톤 (버스 내부 카운팅) | 정류장 외부 미적용, 모델 이식 개념 없음 | 정류장 외부 + 서울→광주 모델 Transfer |

## 2. 작품의 이론 및 기술 현황

### 2.1 핵심 이론

**(1) RandomForest 혼잡도 예측 모델**
- 4개 feature (2026-05-16 weekday 제거 + 2026-05-17 weather/temperature 제거, 단순화): `hour`, `prev_boarding`, `prev_alighting`, `route_count`
- 4단계 분류: 여유 / 보통 / 혼잡 / 매우혼잡 (국토부 표준)
- 학습 데이터: 서울시 차내 혼잡도 API + 승하차 이력
- 모델: `rf_model.pkl` (약 2.9MB, n_estimators=100, max_depth=10), CV 5-fold 0.9960 ±0.0029
- 3단계 폴백: RandomForest → rule_based(`backend/seeds/rule_based.py`, sklearn 의존 0) → DUMMY
- LightGBM 듀얼 트랙은 2026-05-17 단순화로 `archive/ml_lightgbm/`에 이관

**(2) YOLOv11 + DeepSORT 라인 크로싱 카운팅**
- Jetson Orin Nano (CUDA 12.6 / TensorRT 10.3) GPU 추론
- TensorRT FP16 export 시 YOLO 단독 38.5 FPS / PyTorch 8.09 FPS → **4.8배 가속**, mAP50-95 손실 -1.4%
- counter.py 풀 파이프라인(YOLO + DeepSORT + OpenCV) 실측 ~14 FPS — DeepSORT MobileNetV2 임베더 병목
- DeepSORT(`max_cosine_distance=0.3`)로 동일 인물 중복 카운팅 방지
- 라인 크로싱: 정류장 진입선(IN)·탑승선(BOARD) 기준 분리 집계 → `current_waiting = IN - BOARD`

**(3) 광주 BIS API 통합**
- `apis.data.go.kr/6290000/gj_bis` — 광주광역시 버스 도착 정보 실시간 API
- 정류장 ID 매핑: 광주대(3230)=1981, 광주대(3229)=80, 광주대입구(3228)=3219
- Flask 백엔드가 프록시 + 30 req/min 레이트 리밋

### 2.2 기술 현황 (사용 기술)

| 계층 | 기술 | 비고 |
|------|------|------|
| AI/ML | Python 3.10, scikit-learn (RandomForest), **YOLOv11** (Ultralytics), DeepSORT | 혼잡도 = RandomForest, 인원 카운팅 = YOLOv11+DeepSORT |
| Backend | Flask + flask-limiter, MySQL 8.0 / SQLite 폴백, PyMySQL | 9개 API, Blueprint 4개 |
| Frontend | JavaScript (ES6), Chart.js, Leaflet.js, **PWA (Service Worker)** | 학생 PWA + Admin 대시보드 |
| Hardware | Jetson Orin Nano (JetPack 6.x), Raspberry Pi 4 (Kiosk), 7" LCD, USB 카메라 | 1대 카메라, GPU 추론 |
| Infra | Docker Compose, Nginx, crontab (Watchdog) | 자동 복구 |

### 2.3 관련 기술 동향

- **YOLO 진화**: v5(2020) → v8(2023) → **v11(2024)** Ultralytics. 본 작품은 v11n/s를 기본, TensorRT FP16 export로 Jetson Orin Nano에서 YOLO 단독 38.5 FPS 달성 (PyTorch 대비 4.8배).
- **광주 BIS 공공데이터 개방**: 2023년부터 정류장별 실시간 도착 정보 무료 제공, REST API 형태.
- **공공데이터 모델 이식 사례**: 부산대(YOLOv5 + DeepSORT), 뻐정(SSD + LightGBM) 등 단일 지역 학습. BUSTAGO는 **타 지역 학습 데이터 이식** 접근.

## 3. 작품의 개발방법 및 과정

### 3.1 개발 단계 (4 Phase + 사용자 여정)

```
Phase 1. 데이터 수집     Phase 2. 처리·분석    Phase 3. 서비스 제공     Phase 4. 저장·관리
─────────────────       ─────────────────    ──────────────────     ──────────────────
서울시 공공데이터 →  →  RandomForest 학습  →  학생 PWA(혼잡도)    →   DB 적재
광주 BIS API     →  →  YOLOv11+DeepSORT  →  Admin 대시보드       →   재학습 피드백
Jetson 카메라    →                          현장 디스플레이(Pi)
```

### 3.2 시스템 아키텍처 (4계층)

> **이미지 자리**: `docs/02_설계/아키텍처정의서.md` §2 4계층 다이어그램 시각화 (Excalidraw/Draw.io로 깔끔히 재작성)

```
[Layer 4 Frontend] Student PWA  +  Admin Dashboard  (Nginx 정적)
                          ↕  fetch /api/*
[Layer 3 Backend] Flask Blueprints (4종 / API 9개) + Rate Limit + CORS
                ↕ predict()              ↕ SQL
[Layer 2 ML] RandomForest (2.9MB)  [Layer 1 DB] stations / predictions /
             4 feature                          crowd_counts / routes
                ▲                          ▲
                │ feature                  │ POST /api/crowd-count (10s)
[Layer 0 Hardware] Jetson + Camera + Pi Kiosk
                   counter.py (YOLOv11 + DeepSORT + Line Crossing)
```

### 3.3 개발 일정 (2026.03 ~ 2026.06)

| 월 | 주요 작업 | 산출물 |

### 3.4 핵심 개발 기법

- **이중 평가 체계**: 객체 탐지 mAP(P / R / mAP50 / mAP50-95) + 운영 KPI(IN 오차율 ≤15%, BOARD 오차율 ≤20%) 분리 측정
- **데이터 기반 평가** (5/14 회의 P0): 실시간 수동 카운팅 비교 대신 라벨링 데이터셋·녹화 영상 사후 라벨 사용 — 결정론적·재현 가능
- **공개 데이터셋**: CrowdHuman BlurHuman v3 (Keio DBA team, **CC BY 4.0**, 21,990장) — 얼굴 비식별 처리된 버전 채택 (개인정보 절차와 메시지 일치)
- **테스트 자동화**: pytest 59건 PASS (backend·hardware·ml) + GitHub Actions CI
- **장애 대응**: MySQL 연결 실패 시 SQLite 자동 폴백, Jetson/Kiosk crontab Watchdog 자동 재시작
- **API 키 보안**: 환경변수(.env)로 관리, 하드코딩 fallback 제거 (2026-05-16 진단 반영)

> **이미지 자리**: 개발 과정 사진 — (1) HW 도착 사진, (2) Jetson 셋업, (3) PWA 화면, (4) Admin 대시보드, (5) 광주대 정류장 카메라 설치 (예정)

- **의사결정 지원**: "지금 vs 30분 후" 정량 비교로 합리적 행동 선택

### 5.2 운영자 측 기대효과

- **증차 의사결정 정량화**: 시간대별 혼잡도 통계 → 셔틀 6호차 운행 시간대 조정

### 5.3 학술·기술적 의의

- **모델 이식(Transfer) 사례**: 공공데이터 풍부 지역(서울) → 부족 지역(광주) 학습 모델 이식 방법론 제시

- **공개 코드·문서**: GitHub 공개(MIT) — 타 캠퍼스 확장 시 베이스라인

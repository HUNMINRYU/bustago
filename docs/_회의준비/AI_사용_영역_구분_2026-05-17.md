## 2. 책임 매트릭스 (RACI)

R = Responsible (실행자), A = Accountable (책임자), C = Consulted (자문), I = Informed (정보 수신)

| 영역 | 팀원 (류훈민/이트겔/이건영/박건우) | AI (Claude) |
|---|---|---|
| 요구사항 정의 | **R, A** | — |
| 시스템 설계 (spec) | **R, A** | C (자문 — 안 제시) |
| 실행 계획 (plan) | **R, A** | C (자문) |
| 코드 작성 (구현) | A (검토·승인) | **R** (TDD 위임) |
| 테스트 작성 (TDD) | A (시나리오 결정) | **R** (작성 위임) |
| Spec 일치 검증 | **R, A** (리뷰) | — |
| Code Quality 검증 | **R, A** (리뷰) | C (자체 검토) |
| 데이터 수집 | **R, A** (현장 작업) | — |
| 평가 결과 해석 | **R, A** | C |
| 발표·문서 | **R, A** | C (초안 자문) |
| 시연 운영 | **R, A** | — |
| Git 커밋 (계정) | **R** (HUNMINRYU, Geonwoopark38) | — (claude 계정은 co-author 표기) |

→ 모든 영역에서 **A (책임자)는 팀원**. AI는 R 또는 C에만 위치.

## 4. AI 산출물 검증 체인

CONTRIBUTING.md §2 체크리스트와 본 명세서를 결합한 실제 운영 절차:

```
[AI 초안 생성]
       ↓
[1차 검토: spec compliance reviewer]  ← 팀원 또는 별도 AI agent
       ↓ (불일치 시 fix loop)
[2차 검토: code quality reviewer]    ← 팀원 또는 별도 AI agent
       ↓ (품질 이슈 시 fix loop)
[자동 검증: pytest]                   ← CI에서 자동 실행
       ↓ (실패 시 빌드 차단)
[수동 검토: 팀장 커밋]                ← 류훈민이 git commit
       ↓
[자동 검증: GitHub Actions CI]        ← develop push 시 자동
       ↓
[배포 가능]
```

각 단계의 *통과 기준은 팀원이 정의*했고, AI는 그 기준에 맞춰 작업할 뿐.

## 5. 발표·심사 Q&A (5가지 변형)

### Q1. "GitHub에 claude가 contributor로 보이는데 누가 만든 프로젝트입니까?"

A: 본 프로젝트는 광주대 캡스톤 4인 팀의 산출물입니다. Claude는 코드 작성 단계의
lab assistant로 사용했고, 모든 spec·plan·검토·결정·운영은 팀원이 직접 했습니다.
구체적 사용 영역은 `docs/_회의준비/AI_사용_영역_구분_2026-05-17.md`의 RACI 표에
명시되어 있습니다.

### Q2. "AI가 작성한 코드와 팀원이 작성한 코드를 구분할 수 있나요?"

A: 본 프로젝트의 모든 코드는 *어느 단계에서 어떤 검증을 거쳤는지*가 중요하다고
판단합니다. AI 초안 → spec 일치 검토 → 품질 리뷰 → pytest → CI 4단계를 거쳤고,
각 단계의 통과 기준은 팀원이 정의했습니다. 어느 라인을 누가 처음 썼는지는
*책임 소재와 무관*하다는 입장이고, 그 책임 소재 자체는 `CONTRIBUTING.md` §1에
사전 정의되어 있습니다.

### Q3. "평가 대상은 누구의 산출물입니까?"

A: 팀원의 산출물입니다. *어떤 도구를 어떻게 사용했는지에 대한 의사결정*도 평가
대상에 포함된다고 생각합니다. AI 도구 사용 원칙을 5/1에 사전 문서화했고
(`CONTRIBUTING.md`), 5/17 외부 실사 후 본 명세서로 보강했습니다. 도구 활용
역량도 학부 캡스톤 평가 항목이라고 이해합니다.

### Q4. "다른 팀과 비교해 AI 의존도가 높지 않습니까?"

A: 본 프로젝트는 의도적으로 AI를 활용 영역을 명시하고 검증 메커니즘을 구축했다는
점에서 *다른 팀이 AI를 쓰지만 명시 안 한 것보다 투명하다*고 봅니다.
1. CONTRIBUTING.md §2 검토 체크리스트 5건
2. pytest 51건 + CI 자동화
3. 본 RACI 매트릭스
이 셋이 결합되어 AI 산출물의 신뢰성을 사람이 검증한 결과로 전환합니다.

### Q5. "팀원 본인이 직접 코드를 작성할 수 있습니까?"

A: 가능합니다. spec·plan을 팀원이 직접 작성한다는 자체가 *구현 방법을 알고
있다*는 증명입니다. Phase 1의 sample_frames / autolabel / eval_counting 3개
모듈은 TDD red → green 절차를 팀원이 정의했고, 코드 라인 자체는 AI가 채웠지만
"이 함수가 어떤 input → output을 가져야 하는가"는 팀원이 결정했습니다.
시연 당일 즉석에서 코드 변경이 필요하면 팀원이 직접 수정합니다.

## 6. 본 명세서의 의의

AI 사용을 *부정*하거나 *숨기는* 자세보다, **사용 영역을 명시하고 검증 체인을
공개하는 자세**가 평가에서 더 높은 점수를 받는다고 판단함.

학부 캡스톤 평가는 *결과물의 완성도* + *도구 활용 역량* + *팀의 의사결정 능력*
세 축이 모두 평가 대상이고, 본 명세서는 둘째·셋째 축에 대한 응답.

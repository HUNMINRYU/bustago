# BUSTAGO 산출물 감리 보고서

- 작성일: 2026-05-14
- 관점: Clean Architecture, 요구사항 추적성, 테스트 가능성, 문서 완성도, 배포 가능성
- 범위: 저장소 내 코드, 문서, 설정, 테스트, 배포/설치 자료, 발표/시연 산출물
- 제한: 비밀값과 실제 `.env` 내용은 기록하지 않음

## 1. 최종 판정

**제출/발표 전 위험**

SW 데모는 일부 가능해 보이지만, 문서-코드-모델-하드웨어 산출물 사이의 불일치와 0바이트 발표/조사 산출물이 남아 있어 현재 상태를 "완성된 제출물"로 보기 어렵다.

## 2. 한 줄 총평

이 프로젝트는 버스 혼잡도 예측/카운팅 시스템의 골격은 갖췄지만, 발표용 산출물과 실제 실행 가능한 구현 사이의 정합성이 부족한 상태다.

## 5. 문서 완성도 평가

README는 프로젝트 목적, 구조, 빠른 실행 절차를 제공하지만 "README만 보고 처음 보는 사람이 검증 가능"한 수준은 아니다. 특히 `README.md`는 LightGBM 모델 산출물이 존재하는 것처럼 설명하지만 실제 `ml/models/lgbm_model.pkl`은 없고, backend는 `backend/config.py`에서 `rf_model.pkl`을 기본 모델로 사용한다.

`docs/README.md`는 `docs/02_설계/아키텍처정의서.docx`, `DB설계서.docx`, `메뉴구조도_화면설계서.docx`를 링크하지만 해당 `.docx` 파일은 없고 `.md` 파일만 존재한다. 또한 `docs/발표자료/발표대본.docx`, `docs/발표자료/포스터.pdf`, `docs/06_조사데이터/서울시_EDA분석.ipynb`, `설문조사_결과분석.docx` 등은 0바이트다.

문서 전반에 RandomForest, LightGBM, YOLOv8, YOLOv11 설명이 혼재되어 있다. 발표 시 "현재 최종 기술 스택이 무엇인가?"라는 질문에 문서만으로는 일관된 답을 주기 어렵다.

## 6. 코드 산출물 평가

아키텍처는 `backend/routes`, `ml/models`, `frontend/student`, `frontend/admin`, `hardware`로 기능별 분리는 되어 있다. 다만 Clean Architecture 관점에서는 라우트 계층이 예측 호출, DB 저장, 외부 API fallback, 응답 조립을 함께 담당하고 있어 유스케이스/인프라 분리가 약하다.

리스크가 큰 부분은 fallback이 너무 조용하다는 점이다. `backend/routes/predict.py`는 모델 파일 또는 import 실패 시 dummy prediction을 반환하고, `backend/routes/recommend.py`도 ML 실패 시 시간 기반 합성값을 사용한다. 데모 안정성에는 도움이 되지만, 실제 성능을 증명해야 하는 제출/심사 상황에서는 "진짜 모델이 돈 것인지"를 분리해서 보여줘야 한다.

보안 측면에서는 `backend/config.py`에 외부 API 키 fallback 값이 하드코딩된 구조가 있다. 값은 이 문서에 기록하지 않지만, 구조 자체가 제출 전 반드시 제거되어야 할 P0 리스크다. 또한 `backend/routes/crowd.py`의 crowd count POST는 장치 인증이 없어 임의 데이터 주입 가능성이 있다.

프론트엔드는 일부 `innerHTML` 사용이 있고, 외부 API/서버 응답 데이터를 직접 렌더링하는 패턴이 보여 XSS 방어 측면에서 보완이 필요하다.

## 7. 테스트/검증 상태

안전하게 실행한 검증:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest ml/data_collection/test_collect_congestion.py -q -p no:cacheprovider
```

결과: **3 passed**

| 검증 | 상태 | 이유 |
|---|---:|---|
| backend 전체 pytest | 검증하지 못함 | Flask app 생성 시 DB 초기화/테스트 POST로 `backend/bustago.db` 변경 가능 |
| 전체 pytest | 검증하지 못함 | 일부 테스트가 외부 API와 환경변수에 의존 |
| Docker Compose 실행 | 검증하지 못함 | 컨테이너/볼륨 생성 및 DB 파일 변경 가능 |
| ML 학습 | 검증하지 못함 | `lgbm_model.pkl` 생성 등 파일 변경 발생 |
| 하드웨어 카운터 | 검증하지 못함 | 카메라/Jetson/모델 파일/실장 환경 필요 |
| 프론트 UI 수동 시연 | 검증하지 못함 | 서버 기동 필요, 읽기 중심 감리 범위를 초과 |

테스트 커버리지는 핵심 품질을 충분히 보증하지 못한다. 특히 ML 성능, 하드웨어 카운팅 정확도, 실제 버스 API 통합, 프론트 E2E, 배포 시나리오가 자동 검증으로 묶여 있지 않다.

## 9. 치명적 누락/불일치 목록

### P0: 제출/시연 전에 반드시 해결

- `backend/config.py`의 외부 API 키 fallback 하드코딩 구조 제거
- README/문서/코드의 최종 ML 모델 통일
- LightGBM을 최종 모델로 주장할 경우 `lgbm_model.pkl`과 backend 설정 정합화
- YOLOv8/YOLOv11 문서 불일치 정리
- 발표대본, 포스터, 조사/EDA/설문 파일의 0바이트 상태 해소
- fresh clone 기준 실행 가능성 확보

### P1: 품질상 매우 중요

- API 문서화: endpoint, request, response, error code, env var 정리
- backend fallback/dummy 응답을 demo mode와 production mode로 분리
- crowd count POST 인증 또는 최소 device token 검증 추가
- 실제 통합 테스트와 외부 API 없는 테스트 분리
- Docker volume이 `/app/backend` 전체를 덮는 구조 재검토

### P2: 완성도 향상

- 프론트 `innerHTML` 렌더링을 안전한 DOM 생성 방식으로 변경
- `docs/README.md` 링크를 실제 파일명과 일치시킴
- 연구/조사 문서의 AI citation placeholder와 "기입 필요" 제거
- CI 추가: lint/test/build 최소 검증
- 발표용 "실제 동작 범위 vs 데모 fallback 범위" 슬라이드 추가

1. 하드코딩된 외부 API 키 fallback 구조를 제거하고 `.env.example` 기준으로만 동작하게 정리한다.

6. API 명세와 시연 절차를 별도 문서로 고정한다.

8. ML/HW/외부 API/프론트 E2E 검증 결과를 테스트 문서에 연결한다.

## 12. 결론

현재 상태는 **SW 중심 조건부 시연은 가능할 수 있으나, 제출/발표 산출물로는 위험하다.**

가장 큰 이유는 최종 모델과 하드웨어 스택 설명이 문서마다 다르고, 실제 모델 artifact와 backend 설정이 README 주장과 일치하지 않으며, 발표/조사 산출물 일부가 0바이트이기 때문이다.

제출 전에는 최소한 P0 항목을 먼저 정리해야 한다. 특히 "LightGBM을 쓴다", "YOLOv11로 카운팅한다", "실제 API/실제 모델 기반으로 예측한다"는 주장을 하려면 파일, 코드 설정, 테스트 결과, 문서가 같은 말을 해야 한다.

# BUSTAGO 하네스 아키텍처 설계서

## 1. 개요

BUSTAGO 프로젝트의 자동화된 빌드 파이프라인을 위한 에이전트 팀 하네스 설계서.
ML 파이프라인 완성 → Flask Backend 구축 → Frontend PWA/Dashboard 구축을 에이전트 팀이 자동으로 수행한다.

### 1.1 실행 모드

**에이전트 팀 (Agent Team)** 모드를 사용한다.

- Backend가 ML 모델 출력 형식을 알아야 하고, Frontend가 API 응답 형식을 알아야 하므로 에이전트 간 직접 통신(SendMessage)이 필요
- QA가 경계면을 실시간으로 교차 검증하여 불일치를 조기에 발견

### 1.2 아키텍처 패턴

**Pipeline + Fan-out** 복합 패턴

```
Phase 2: [ML Engineer] ─── 순차 (Pipeline) ──→ 모델 계약서
                                                    │
Phase 3:                    ┌─ [Backend Engineer] ──┤── API 계약서 ─┐
         병렬 (Fan-out) ───├─ [Frontend Engineer] ──┤              │
                            └─ [QA Inspector] ──────┘── QA 리포트 ─┘
```

## 4. 오케스트레이터 워크플로우

### Phase 1: 준비
- `_workspace/` 디렉토리 생성
- 기존 ML 코드 상태 확인 (collect_boarding.py, collect_weather.py, build_features.py)
- 현재 Feature 스키마를 `_workspace/00_input/`에 저장

### Phase 2: ML 파이프라인 빌드 (Team 1 -- ML 단독)
- TeamCreate로 ml-engineer 단독 팀 구성
- 구현 대상:
  1. `collect_congestion.py` -- 서울시 버스도착정보 API 차내혼잡도 수집
  2. `pipeline.py` -- 3개 수집기 통합 오케스트레이션
  3. `train_rf.py` -- Random Forest 학습/평가/직렬화
  4. `predict.py` -- 모델 추론 인터페이스
- 산출물: `_workspace/01_ml_model_contract.json` (모델 계약서)
- 팀 정리 (TeamDelete)

### Phase 3: 앱 빌드 (Team 2 -- Backend + Frontend + QA 병렬)
- TeamCreate로 3명 팀 구성
- **backend-engineer**: ML 계약서 참조 → Flask 앱 + REST API 구현 → API 계약서 생성
- **frontend-engineer**: 정적 UI 먼저 구현 → API 계약서 수신 후 연동 코드 구현
- **qa-inspector**: 각 모듈 완성 직후 점진적 교차 검증
- 팀원 간 SendMessage로 실시간 소통

### Phase 4: 통합 검증
- QA 리포트 확인, 미해결 이슈 수정 요청

### Phase 5: 정리
- 팀 정리, `_workspace/` 보존, 결과 요약 보고

## 6. QA 검증 체크포인트

점진적 QA -- 전체 완성 후 1회가 아닌, 각 모듈 완성 직후 교차 검증.

| Checkpoint | 트리거 | 검증 내용 |
|-----------|--------|----------|
| 1 | ML predict.py 완성 | Feature 이름/순서 일치, 반환값 shape, 모델 경로 |
| 2 | Backend /api/predict 완성 | 쿼리 파라미터→Feature 변환, 응답 타입, label_map 일치 |
| 3 | Frontend api.js 완성 | fetch URL 일치, 응답 JSON 키, 혼잡도 색상 매핑 |
| 4 | 전체 완성 | ARS번호 형식(문자열 5자리), 시간 형식(0-23 int), 날씨 코드 일관성 |

### 6.1 BUSTAGO 경계면 검증 항목

#### ML ↔ Backend
- predict.py 입력 파라미터명 == API 쿼리 파라미터명
- predict.py 반환 타입(int 0-3) == API 응답 level 필드
- Feature 컬럼 순서: 학습 시 == 예측 시
- 모델 파일 경로 참조 정확성

#### Backend ↔ Frontend
- API 응답 JSON 키명 == Frontend 접근 키
- 혼잡도 level(0-3) + label(여유/보통/혼잡/매우혼잡) 매핑 양쪽 동일
- API URL 경로 == Frontend fetch URL
- CORS 설정 == Frontend origin

## 7. 에러 핸들링 전략

캡스톤 프로젝트 특성상 "계속 진행"이 "완벽한 품질"보다 중요하다.

| 상황 | 폴백 전략 |
|------|----------|
| ML 모델 미완성 | Backend가 더미 예측 반환 (`level: 1, label: "보통"`) |
| MySQL 미설치 | SQLite로 폴백 |
| API 키 누락 | 해당 데이터 소스 비활성화 (서버는 기동) |
| QA 불일치 다수 | 크래시 유발 항목만 우선 수정, 나머지는 리포트에 기록 |
| 에이전트 실패 | 1회 재시도 → 재실패 시 해당 결과 없이 진행, 최종 보고서에 명시 |

## 9. API 엔드포인트 설계

| 메서드 | 경로 | 설명 | 파라미터 |
|--------|------|------|----------|
| GET | /api/predict | 혼잡도 예측 | station_id, hour, weekday(opt) |
| GET | /api/stats | 통계 조회 | station_id, period(today/week/month) |
| GET | /api/stations | 정류장 목록 | - |
| GET | /api/weather/current | 현재 날씨 | - |

### 응답 형식 (공통)
```json
{
  "status": "ok",
  "data": { ... },
  "timestamp": "2026-03-29T14:00:00"
}
```

### /api/predict 응답 예시
```json
{
  "status": "ok",
  "data": {
    "station_id": "22011",
    "station_name": "지하철2호선강남역",
    "hour": 8,
    "prediction": {
      "level": 2,
      "label": "혼잡",
      "probabilities": [0.1, 0.2, 0.5, 0.2]
    },
    "recommendation": "혼잡이 예상됩니다. 다음 시간대를 추천합니다.",
    "next_hour_prediction": {
      "level": 1,
      "label": "보통"
    }
  },
  "timestamp": "2026-03-29T14:00:00"
}
```

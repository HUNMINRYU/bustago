## 5. 서울 데이터 → 광주 적용 — 타당성 정밀 평가

> **발표 심사위원이 가장 먼저 공격할 지점. 별도 강조.**

### 모델의 실제 동작
`feature_importances_` 실측상 **hour가 예측의 81.4%를 결정**. route_count 9.9%, prev_boarding 4.9%, prev_alighting 3.8%. 즉 운영 모델은 통계적으로 **"시간대 기반 확률 테이블의 ML 포장"**에 가깝다.

### 타당성 근거 (방어 가능)
1. 광주 BIS에 혼잡도 데이터가 없음을 API 명세로 확인 — 서울 데이터 사용의 불가피성 근거 있음(`광주_서울_API_혼잡도_비교.md`).
2. 4단계 분류는 국토부 대중교통 표준 기반 — 서울/광주 라벨 의미 동일.
3. "출퇴근/통학 시간대 = 혼잡"은 도시 무관 보편 패턴 — hour 지배 구조가 광주에도 방향성은 맞음.
4. `모델_신뢰성_한계_진술서.md`로 한계 선제 공개 — 발표 방어 준비됨.

### 타당성 한계 (공격 지점 — 반드시 대비)
1. **라벨이 서울 대형 정류장 일승차량 분위수** — 광주대 정류장 절대 승차량은 수백 배 적음. "서울 기준 여유 = 광주 기준 매우혼잡"의 역설. **최우선 공격 지점.**
2. **입력 피처와 라벨의 도메인 스케일이 다름** — 추론 시 카메라 카운트(0~20명)는 서울 학습 데이터 하위 46%로 처리됨 → hour만 남음.
3. **route_count 외삽** — 학습 19~26 vs 광주 2~8. `hour=8`에서 rc에 따라 예측이 1~2단계 왜곡.
4. **셔틀 노선 미학습** — `routes_gj.py`의 SHUTTLE1~6(rc=2)은 학습 데이터에 없음.

### 발표 권장 프레이밍
> "현재 ML은 **시스템 파이프라인 동작을 증명하는 구조 검증 단계**입니다. Accuracy 수치는 모델 구조 검증치이며, 카메라 카운팅으로 광주 자체 데이터를 수집 중이고 경진대회 이후 광주 특화 재학습 트랙으로 전환합니다."

→ "라벨이 서울 스케일 분위수"라는 점을 **발표자가 먼저 꺼내** 한계 진술서 논거로 선제 방어할 것.

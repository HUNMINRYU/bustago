## 슬라이드 3: 솔루션 개요
- 3줄 요약: AI 카운팅 + ML 예측 + PWA 표시
- 시스템 블록 다이어그램 (카메라→Jetson→서버→학생/운영자)
- 발표 포인트: 기존 수동 운영 대비 자동화 포인트 강조

## 슬라이드 4: 기술 스택
- 보드별 역할: Jetson Orin Nano(AI 카운팅) / Raspberry Pi(Kiosk) / 서버(Flask+ML)
- 왜 Jetson인가: Pi 4는 2~5 FPS → DeepSORT 중복 카운팅 불가 / Jetson 25~40 FPS → 정확
- 발표 포인트: 교수 피드백 반영 — Pi→Jetson 변경 근거 명확히 제시

## 슬라이드 5: AI 카운팅 설명
- YOLOv11-nano + DeepSORT Track ID
- Line Crossing: IN 라인 / BOARD 라인
- 중복 카운팅 방지: 같은 Track ID 1회만 카운트
- **Baseline 측정 (2026-05-16)**: yolo11n × CrowdHuman BlurHuman public val
  → Precision 0.663 / Recall 0.395 / **mAP50 0.458** / mAP50-95 0.258
  → 군중 밀집 환경 reference. 광주대 정류장은 단순(2~5명)이라 self_v1 val에서 더 높게 예상
- **TensorRT FP16 가속 측정 (2026-05-23, Jetson Orin Nano, COCO8 val)**:
  | 포맷 | ms/im | FPS | mAP50-95 |
  |---|---|---|---|
  | PyTorch (.pt) | 123.68 | 8.09 | 0.6161 |
  | **TensorRT (.engine) FP16** | **25.97** | **38.5** | 0.6074 |
  → **YOLO 단독 4.8배 가속, mAP 손실 1.4%**
- **풀 파이프라인 실측 (counter.py)**: ~14 FPS — DeepSORT MobileNetV2 임베더 병목
  · YOLO 가속이 풀 FPS로 안 옮겨지는 이유 = 트래커가 더 무거움. 정직하게 명시.
- 시연: counter.py --debug 화면 캡처 또는 실시간
- 발표 포인트: Track ID 기반 중복 방지 로직을 그림으로 설명 + baseline 수치로
  "데이터 기반 평가" 증명 (5/14 회의 P0 반영). TensorRT 가속 결과는 단독 4.8배로
  강조하되, 풀 파이프라인 14 FPS는 솔직하게 (트래커 병목 향후 개선 여지)

## 슬라이드 6: ML 혼잡도 예측 모델
- **4 feature** (hour, prev_boarding, prev_alighting, route_count) — 2026-05-16 weekday 제거 + 2026-05-17 weather/temperature 제거 (MVP 단순화)
- **현재 운영 RandomForest (2026-05-16 재학습, n_estimators=100, depth=10)**:
  - Accuracy **0.9983** / F1 macro **0.9983** / CV 5-fold **0.9960 ±0.0029** / 모델 크기 2.9MB (4 feature, 2026-05-17 재학습)
  - Feature importance: hour 0.81, route_count 0.10, prev_boarding 0.05, prev_alighting 0.04 (hour 비중 증가)
  - n=10 → n=100 변경(진단 P1)으로 CV std 절반 (0.0013 → 0.0007), 안정성 향상
- Rule-based 폴백 (2026-05-17): `backend/seeds/rule_based.py` — ML 실패 시 자동 전환, sklearn 의존 0 (MVP 단순화 묶음 B 반영)
- 서울 데이터 학습 → 광주 적용 (혼잡도 분류체계 국토부 표준)
- 발표 포인트: 국토부 표준 분류체계 근거로 전이 타당성 + 진단 P0/P1 정량 개선 명시

## 슬라이드 11: 성과 및 검증
- pytest **59 PASS** (backend·hardware·ml, 2026-05-17 STATUS 기준)
- RandomForest 혼잡도 모델: Accuracy 0.9983 / CV 5-fold 0.9960±0.0029 (n=100, **4 feature**, 2026-05-17 재학습)
  · 합성/quantile 라벨링 한계는 `모델_신뢰성_한계_진술서.md` 명시
  · Rule-based 폴백(2026-05-17 추가)으로 ML 실패 시 자동 전환
- **YOLO 카운팅 baseline (2026-05-16)**: yolo11n × CrowdHuman public val
  - Precision 0.663 / Recall 0.395 / **mAP50 0.458** / mAP50-95 0.258
  - val 1,857장 / 인스턴스 54,626건 (avg 29.4 person/image)
  - 출처: Keio DBA team CrowdHuman BlurHuman v3 (CC BY 4.0, 21,990장)
- **TensorRT FP16 가속 (2026-05-23, Jetson Orin Nano, COCO8 val)**:
  - PyTorch 8.09 FPS (123.68 ms/im) → **TensorRT 38.5 FPS (25.97 ms/im)**, **4.8배 가속**
  - mAP50-95 손실: 0.6161 → 0.6074 (-1.4%, 허용 범위)
  - 풀 파이프라인(counter.py: YOLO+DeepSORT+OpenCV) 실측 ~14 FPS — DeepSORT 임베더가 병목,
    YOLO 단독 가속이 풀 FPS로 옮겨지지 않음. 향후 트래커 경량화로 개선 여지.
- API 응답 800ms → 23ms (LRU 캐시 적용)
- 코드 라인 수 / 커밋 수 등 (팀원 기입)
- 발표 포인트: 정량 수치로 신뢰도 확보. baseline은 **데이터 기반 평가**(5/14 회의 P0)
  결과로, 추후 광주대 자체 데이터 fine-tune으로 개선 폭 측정 예정

## 슬라이드 14: Q&A
- 예상 질문 및 답변 준비:
  1. "광주 데이터가 없는데 서울 모델을 쓰는 이유?"
     → 국토부 혼잡도 분류 표준 동일 적용, 추후 Ground Truth로 파인튜닝 예정
  2. "카메라 1대로 정확한 카운팅이 가능한가?"
     → 정류장 단일 진입로 구조 + Line Crossing 방식으로 정확도 확보
  3. "Pi 4 대신 Jetson을 쓰는 비용 대비 효과는?"
     → DeepSORT 실시간 처리 필수 / FPS 부족 시 중복 카운팅 발생 → 정확도 저하 불가피
  4. "AI 카운팅 정확도는 어떻게 검증했는가?" *(예상 신규 질문)*
     → CrowdHuman BlurHuman public val 1,857장으로 baseline yolo11n 측정:
        mAP50 0.458 / Recall 0.395. 광주대 자체 fine-tune 후 self_v1 val + 영상 사후
        라벨로 IN/BOARD 오차율 비교 예정. 데이터 기반·결정론적 평가 채택.
  5. "데이터셋 라이선스와 개인정보 처리는?"
     → CrowdHuman BlurHuman은 CC BY 4.0 + 얼굴 비식별 블러 처리됨. 자체촬영분은
        `docs/03_구축/촬영_동의_및_삭제_절차.md`(2026-12-31 폐기) 적용 + `anonymize_faces.py`
        후처리.
  6. **"GitHub contributor에 claude가 있는데 팀이 만든 게 맞습니까?"** *(2026-05-17 신규)*
     → Claude는 lab assistant 역할이고 의사결정자가 아닙니다. 모든 spec·plan·검토·
        결정·운영은 팀원이 직접 했고, AI 산출물은 spec compliance + code quality
        2단계 리뷰 + pytest 59건 + GitHub Actions CI로 자동 검증됩니다. RACI 매트릭스
        + 검증 체인은 `docs/_회의준비/AI_사용_영역_구분_2026-05-17.md`에 명시.
  7. **"평가 대상은 누구의 산출물입니까?"** *(2026-05-17 신규)*
     → 팀원의 산출물입니다. 도구 활용 방식의 의사결정도 평가 대상에 포함된다고
        이해하고, 5/1에 `CONTRIBUTING.md`로 AI 사용 원칙을 사전 문서화했습니다.
  8. **"모델 정확도 0.9993이 비현실적이지 않습니까?"** *(2026-05-17 신규)*
     → 솔직히 비현실적입니다. 합성/quantile 라벨링 결과이고, 광주 실측은 0.7~0.8이
        현실적 기대치입니다. 본 한계는 `docs/04_테스트/모델_신뢰성_한계_진술서.md`에
        명시되어 있고, 광주 자체 데이터로 검증 후 갱신할 예정입니다.
  9. **"git history에 API 키가 노출됐는데 왜 안 바꾸셨습니까?"** *(2026-05-17 신규)*
     → 의도된 risk-managed 결정입니다. (1) 광주 BIS는 read-only 공공 OpenAPI라
        키 노출되어도 권한 확장·DB 변조 불가. (2) 새 키 발급은 활성화 1~2h 대기
        필요해 시연 직전 교체가 더 위험. (3) 작업 트리 노출은 이미 제거(`6e65d37`
        + `82df0ec`)했고, git history 정리는 `git filter-repo`로 평가 후 일괄.
        책임 명문화: `docs/API_키_rotate_가이드_2026-05-16.md` §0, §5.5

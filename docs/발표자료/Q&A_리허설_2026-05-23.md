## 0. 개요

**리허설 목적**
경진대회 Q&A 5분은 발표 10분보다 점수 변동이 크다. 심사위원은 이미 슬라이드를 봤으므로 공격 질문을 준비해 온다. 이 파일은 가장 위험한 질문부터 최근 추가된 기술 질문까지 총 19건을 *암기 수준*으로 숙달하기 위한 카드 세트다.

**사용법**
- 한 사람이 심사위원 역할, 한 사람이 발표자 역할을 맡는다.
- 이 파일을 프린트하거나 화면에 띄운 뒤 질문 카드를 **무작위로** 뽑아서 연습한다.
- 타이머 30초 설정 후 답변 시작. 시간 초과 시 상대방이 손들어 알린다.
- 세션 간 역할 교체 필수 — 발표자 누구든 모든 질문에 답할 수 있어야 한다.

### LANDMINE-1. "라벨이 서울 대형 정류장 스케일 분위수인데 광주에 적용 가능한가?"

**왜 위험한가:** 종합점검 §5에서 "발표 심사위원이 가장 먼저 공격할 지점"으로 명시된 최우선 공격 포인트. 논리적으로 완전히 틀린 말이 아니기 때문에 부정하면 오히려 신뢰를 잃는다.

**30초 답변 멘트**
> "날카로운 지적입니다. 솔직히 이건 한계입니다. 서울 대형 정류장 일승차량을 분위수로 자른 라벨이라 광주대 정류장의 절대 인원과 스케일이 다릅니다. 그러나 세 가지 방어 근거가 있습니다. 첫째, 광주 BIS API에 혼잡도 데이터 자체가 없어서 서울 데이터 사용이 유일한 선택입니다. API 명세로 확인된 사실입니다. 둘째, 4단계 분류 체계는 국토부 대중교통 표준 기반으로 서울·광주 모두 동일합니다. 셋째, feature importance 실측 결과 hour가 81%를 차지합니다. 즉 이 모델은 통학·통근 시간대 패턴 기반이고, 그 패턴은 도시 무관하게 보편적입니다. 현재는 시스템 구조 검증 단계이고, 광주 자체 데이터 수집 후 재학습 트랙이 별도로 있습니다."

**핵심 talking points 3개**
1. 광주 BIS API에 혼잡도 없음 — API 명세 기반 사실 (`광주_서울_API_혼잡도_비교.md` 근거)
2. hour 81% 지배 → 모델은 사실상 시간대 패턴 테이블 → 도시 무관 보편 패턴
3. 한계는 인지하고 있고, 모델 신뢰성 한계 진술서로 선제 공개됨

**압박될 때 fallback line**
> "저희도 이 한계를 알고 있습니다. 그래서 한계 진술서를 미리 작성해 공개했습니다. 광주 현장 데이터 수집 트랙이 진행 중이고, 경진대회 이후에 광주 특화 재학습을 할 예정입니다."

**답변 후 전환**
> "다음 질문 있으시면 받겠습니다."

### LANDMINE-2. "모델 정확도 0.9983이 비현실적이지 않은가?"

**왜 위험한가:** 이 수치가 슬라이드에 그대로 나온다. 심사위원이 "너무 좋다"고 느끼면 신뢰도가 오히려 떨어진다. 방어보다 선제 인정이 훨씬 강하다.

**30초 답변 멘트**
> "솔직히 비현실적입니다. 이 수치는 합성·분위수 라벨링 결과이고, 모델이 사실상 서울 데이터에서의 시간대 패턴을 학습했기 때문에 높게 나옵니다. 광주 실측 데이터로 평가하면 0.7~0.8이 현실적인 기대치입니다. 저희는 이 한계를 미리 알고 `모델_신뢰성_한계_진술서.md`에 문서화했습니다. 이 수치의 의미는 ML 파이프라인과 백엔드 연동이 end-to-end로 동작한다는 구조 검증치로 해석해 주십시오. 실 광주 데이터 검증 결과는 경진대회 이후 별도 보고 예정입니다."

**핵심 talking points 3개**
1. 비현실적임을 팀이 이미 인지하고 있고 문서화했다 (약점을 강점으로)
2. 합성/quantile 라벨링 + random split이라 train/test 분포 누수 가능성
3. 0.9983은 구조 검증치, 광주 실측 기대치는 0.7~0.8

**압박될 때 fallback line**
> "약점을 숨기지 않고 선제 공개했다는 자체가 저희 팀의 데이터 리터러시를 보여주는 근거라고 생각합니다."

**답변 후 전환**
> "모델 구조 자체에 대해 더 궁금한 점 있으시면 여쭤봐 주세요."

### LANDMINE-3. "GitHub contributor에 claude 표시되는데 팀이 만든 게 맞나?"

**30초 답변 멘트**
> "네, Claude를 도구로 사용했습니다. 역할을 명확히 말씀드리면, Claude는 코드 작성 단계의 lab assistant입니다. 모든 요구사항 정의·시스템 설계·실행 계획·검토 결정은 팀원이 직접 했습니다. AI 산출물은 spec 일치 검토, 코드 품질 검토, pytest 59건, GitHub Actions CI 4단계를 팀원 기준으로 검증했습니다. 이 원칙은 5/1에 CONTRIBUTING.md로 사전 문서화했습니다. 도구 활용 역량도 캡스톤 평가 항목이라고 생각하고, 사용 영역을 투명하게 명시했습니다."

3. 5/1 CONTRIBUTING.md로 AI 사용 원칙 *사전* 문서화 — 들켜서 답한 게 아님

**압박될 때 fallback line**
> "AI 사용을 숨기지 않고 먼저 문서화한 것이 저희 팀의 입장입니다. 어떤 도구를 어떻게 쓸지 결정한 것도 팀원의 역량입니다."

**답변 후 전환**

### Q-01. "광주 데이터가 없는데 서울 모델을 쓰는 이유?"

**원문 (§14-1):** "광주 데이터가 없는데 서울 모델을 쓰는 이유?"

**30초 답변 멘트**
> "두 가지입니다. 첫째, 광주 BIS API를 직접 확인했더니 혼잡도 필드 자체가 없습니다. 이건 추정이 아니라 API 명세 기반 사실입니다. 둘째, 혼잡도 4단계 분류는 국토부 표준 기반이라 서울·광주가 같은 기준입니다. 광주 자체 데이터는 현장 카메라 카운팅으로 지금 수집 중이고, 경진대회 이후 재학습 트랙으로 전환합니다."

**follow-up 1:** "그러면 지금 보여주는 혼잡도 표시는 의미가 있는 건가요?"
> "시스템 통합 데모 목적입니다. ML 파이프라인·백엔드·PWA 연동이 동작함을 보이는 단계이고, 학생에게 실제로 서비스하는 운영 단계는 광주 데이터 학습 후입니다."

**follow-up 2:** "광주 데이터 수집은 언제 완료됩니까?"
> "5/22~5/29 수집, 5/25~5/29 YOLO fine-tune, 6/2~6/3 counting 오차율 평가 일정입니다."

**부정 신호 차단 멘트**
> "데이터 없는 게 아쉬운 것은 맞습니다. 그러나 대안 데이터를 쓸 수밖에 없는 이유가 명확하고, 보완 계획도 구체적입니다."

### Q-02. "카메라 1대로 정확한 카운팅이 가능한가?"

**원문 (§14-2):** "카메라 1대로 정확한 카운팅이 가능한가?"

**30초 답변 멘트**
> "광주대 셔틀 정류장은 단일 진입로 구조입니다. 사람이 버스를 타려면 반드시 한 방향 라인을 통과합니다. 저희는 Line Crossing 방식으로 IN 라인과 BOARD 라인 두 개를 설정하고, 같은 Track ID는 1회만 카운트해서 중복을 방지합니다. 1대 카메라가 단일 진입로 전체를 커버하면 충분합니다."

**follow-up 1:** "옆에서 들어오는 사람은요?"
> "정류장 구조 설계 단계에서 진입로 단일성을 전제로 설계했습니다. 다중 진입로가 있다면 카메라를 추가하거나 라인 위치를 조정해야 하는 확장 항목입니다."

**부정 신호 차단 멘트**
> "한 대로 모든 환경을 커버한다는 주장이 아닙니다. 광주대 정류장의 구체적인 물리 구조에 최적화한 설계입니다."

### Q-03. "Pi 4 대신 Jetson을 쓰는 비용 대비 효과는?"

**원문 (§14-3):** "Pi 4 대신 Jetson을 쓰는 비용 대비 효과는?"

**30초 답변 멘트**
> "Pi 4는 2~5 FPS밖에 안 나옵니다. DeepSORT는 프레임마다 Track ID를 이어줘야 하는데, 5 FPS에서는 같은 사람이 다음 프레임에 다른 ID로 인식돼 중복 카운팅이 발생합니다. Jetson Orin Nano는 TensorRT FP16 기준 YOLO 단독 38.5 FPS, 풀 파이프라인 약 14 FPS입니다. 중복 카운팅 없는 정확한 카운팅을 위해 최소 10 FPS 이상이 필요하고 Jetson이 이를 충족합니다. Pi는 교수 피드백 반영 후 Jetson으로 전환 결정을 내렸습니다."

**follow-up 1:** "가격 차이가 크지 않나요?"
> "Jetson Orin Nano는 약 15만원대입니다. 카운팅 정확도가 핵심인 시스템에서 FPS 부족으로 인한 데이터 오류는 비용으로 해결해야 하는 문제라고 판단했습니다."

**부정 신호 차단 멘트**
> "비용이 더 드는 건 맞습니다. 그러나 정확도가 핵심인 시스템에서 성능 부족 장비를 쓰면 결과 전체가 신뢰를 잃습니다."

### Q-04. "AI 카운팅 정확도는 어떻게 검증했는가?"

**원문 (§14-4):** "AI 카운팅 정확도는 어떻게 검증했는가?"

**30초 답변 멘트**
> "두 단계입니다. 첫째, CrowdHuman BlurHuman public val 1,857장으로 yolo11n baseline을 측정했습니다. mAP50 0.458, Recall 0.395입니다. 군중 밀집 환경 기준이라 광주대 정류장의 2~5명 환경에서는 더 높게 예상됩니다. 둘째, 5/22~5/29 광주대 자체 데이터 수집 후 fine-tune을 진행하고, 6/2~6/3에 영상 사후 라벨링으로 IN/BOARD 오차율을 실측합니다. 데이터 기반, 결정론적 평가를 채택했습니다."

**follow-up 1:** "지금 시연에서 오차가 몇 명이나 나오는지 알고 있나요?"
> "5/21 시연 영상이 있고 6/2~6/3에 사후 라벨링을 통해 최초 측정값을 뽑습니다. 현재는 ±2명 이내 목표치만 설정되어 있고 실측값은 평가 중입니다."

**부정 신호 차단 멘트**
> "측정값이 아직 없다는 점은 솔직히 말씀드립니다. 그래서 검증 일정을 구체적으로 잡았습니다."

### Q-10. "TensorRT YOLO 단독 38.5 FPS인데 풀 파이프라인이 14 FPS인 이유는?"

**30초 답변 멘트**
> "병목이 DeepSORT의 MobileNetV2 임베더에 있습니다. TensorRT로 YOLO는 4.8배 가속했지만, DeepSORT는 각 검출 결과마다 MobileNetV2로 128차원 feature vector를 뽑아 비교합니다. 이 임베더가 TRT 가속 없이 CPU 또는 미최적화 GPU에서 동작해서 병목이 됩니다. YOLO 가속이 풀 파이프라인으로 전달되지 않는 이유입니다. 저희는 이 사실을 슬라이드에 정직하게 명시했고, 향후 임베더 경량화로 20 FPS 이상 달성이 목표입니다."

**압박될 때 fallback line**
> "병목을 알고 있고, 솔직하게 공개했습니다. 해결 방향도 있습니다."

### Q-11. "DeepSORT 병목 알면서 왜 안 바꿨나?"

**30초 답변 멘트**

**압박될 때 fallback line**

## 5. "절대 하지 말 것" 금기 사항

**1. "잘 모르겠는데요" 절대 금지**
- 대신: "현재 미구현된 부분이고, [이유]로 [시점]에 개선 예정입니다"

**2. 방어적·변명 톤 금지**
- 나쁜 예: "어쩔 수 없었어요", "시간이 부족했어요"
- 좋은 예: "트레이드오프를 인지하고 선택했습니다"

**3. AI/툴 사용 부정 절대 금지**
- 나쁜 예: "제가 직접 다 짰습니다"
- 좋은 예: "lab assistant로 활용했고, 의사결정과 검증은 팀이 했습니다"

**4. 수치 즉흥 발명 금지**
- "아마 80% 정도 됩니다" — 근거 없으면 하지 말 것
- 대신: "정확한 수치는 측정 완료 후 보고드리겠습니다"

**5. 질문 중간에 질문으로 되받아치기 금지**
- "그건 무슨 의미로 여쭤보시는 건가요?" — 시간 낭비, 방어적으로 보임
- 대신: 질문을 하나 골라서 정면으로 답하기

**6. "저희 프로젝트의 한계는 알고 있습니다"로 시작하는 허허벌판 공감 금지**
- 한계를 말했으면 바로 "그러나 [근거]로 [방향]으로 대응합니다"로 연결할 것

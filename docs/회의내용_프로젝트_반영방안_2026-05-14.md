# 2026-05-14 회의내용 프로젝트 반영 방안

- 기준 회의록: `docs/회의내용정리_2026-05-14.md`
- 작성일: 2026-05-14
- 목적: 회의에서 나온 요구사항을 현재 BUSTAGO 저장소 상태와 대조하고, 제출/시연/경진대회까지 실제로 적용할 작업 방안을 정리한다.
- 원칙: 회의에서 지적된 항목을 "말로 설명 가능한 수준"이 아니라 코드, 데이터, 테스트, 문서 산출물로 남기는 것을 목표로 한다.

## 1. 결론

회의 내용은 현재 프로젝트의 방향과 대체로 맞지만, **YOLOv11 학습/평가 산출물**, **촬영 동의 절차**, **하드웨어 실측 검증**, **문서-코드 정합성**이 아직 부족하다.

즉시 적용 우선순위는 다음 순서다.

1. 하드웨어 도착 후 Jetson 전원, 카메라 케이블, 카메라 인식부터 검증한다.
2. `yolo11n.pt` 사전학습 모델로 먼저 baseline 카운팅을 돌린다.
3. 공개 데이터와 자체 촬영 데이터를 모아 YOLOv11 fine-tuning용 데이터셋을 만든다.
4. 8:2 학습/검증 분리, 증강, 정확도 측정 결과를 `docs/04_테스트/`에 채운다.
5. 촬영 동의/삭제 절차 문서를 만들어 개인정보 이슈를 발표 전에 차단한다.
6. MQTT는 당장 구현하지 말고 확장 아키텍처 후보로만 문서화한다.

## 3. 현재 프로젝트에 이미 반영된 것

### 3.1 AI 카운팅 기본 구현

`hardware/counter.py`는 YOLOv11, DeepSORT, Line Crossing, `/api/crowd-count` 전송 구조를 이미 갖고 있다.

확인된 요소:

- YOLOv11 모델 경로 인자: `--model yolo11n.pt` 또는 `yolo11n.engine`
- 탐지 클래스 인자: `--classes`, 기본값 `0` person
- 라인 설정: `--in-line`, `--board-line`
- backend 전송: `--server`, `--station-id`, `--post-interval`
- 현재 대기 인원 계산: `count_in - count_board`

즉, "추론 스크립트가 없다"는 상태는 아니다. 문제는 **실제 데이터 기반 학습과 평가 산출물이 아직 없다**는 점이다.

### 3.2 Backend 카운팅 API

`backend/routes/crowd.py`는 다음 API를 제공한다.

| API | 역할 |
|---|---|
| `POST /api/crowd-count` | Jetson 카운팅 데이터 저장 |
| `GET /api/crowd-count?station_id=...` | 최신 카운팅 조회 |
| `GET /api/crowd-count/history?station_id=...` | 카운팅 이력 조회 |

현재 구조는 회의에서 언급된 Flask 직접 전송 방식과 일치한다. 10개 미만 정류장 시연 규모에서는 REST 방식이 현실적이다.

### 3.3 광주 BIS와 저상버스 표시

`backend/routes/stations.py`는 광주 BIS의 `arriveInfo`, `lineInfo`, `gj-stops`를 제공한다. `frontend/student/app.js`는 도착 정보의 `LOW_BUS` 값을 보고 `저상` 태그를 표시한다.

따라서 회의에서 나온 "저상버스·교통약자 정보 제공" 방향은 학생 화면에 일부 반영되어 있다. 다만 발표 자료와 Admin 화면에서는 이 가치가 충분히 드러나지 않는다.

## 4. 현재 프로젝트의 부족한 점

### 4.1 YOLOv11 학습은 준비 단계다

현재 존재하는 파일:

- `hardware/train_yolo.py`
- `hardware/configs/bustago_person.yaml`
- `hardware/requirements-train.txt`

하지만 실제 학습에 필요한 다음 산출물은 확인되지 않는다.

- `datasets/bustago_person/images/train`
- `datasets/bustago_person/images/val`
- `datasets/bustago_person/labels/train`
- `datasets/bustago_person/labels/val`
- 학습 로그
- validation 결과
- baseline 대비 개선 수치
- 현장 카운팅 정확도 결과

회의에서 "YOLOv11 모델 학습이 전혀 준비되지 않았다"는 지적은 정확히는 다음처럼 해석해야 한다.

> 학습 코드의 뼈대는 있으나, 데이터셋과 평가 결과가 없으므로 발표에서 "학습 완료"라고 말할 수 없는 상태다.

### 4.2 정확도 리포트가 비어 있다

`docs/04_테스트/AI_카운팅_정확도_리포트_템플릿.md`는 형식은 좋지만 아직 `[기입 필요]` 상태다.

이 문서는 경진대회와 발표에서 가장 공격받기 쉬운 부분이다.

예상 질문:

- "카메라 카운팅이 실제 사람 수와 얼마나 맞습니까?"
- "사전학습 모델과 fine-tuning 모델의 차이가 있습니까?"
- "조명과 각도에 따라 오차가 얼마나 납니까?"
- "데이터 증강이 실제로 성능을 올렸습니까?"

현재 상태에서는 이 질문에 수치로 답하기 어렵다.

### 4.3 개인정보 처리 절차가 없다

회의록은 촬영 동의와 삭제 절차를 명확히 요구한다. 현재 저장소에는 이를 실제 운영 절차로 고정한 문서가 없다.

필요한 문서:

- 촬영 동의 안내문
- 촬영 거부자 처리 절차
- 요청 시 삭제 절차
- 원본 영상 보관 기간
- 발표/패널에 얼굴이 보이는 자료를 사용할 때의 비식별 처리 기준

### 4.4 MQTT는 지금 구현 대상이 아니다

회의에서 MQTT는 부산대 사례의 확장성 포인트로 언급됐다. 현재 BUSTAGO는 Flask REST API로 Jetson 데이터를 직접 전송한다.

현재 규모:

- 광주대 인성관 중심
- 정류장 1곳 또는 소수 정류장
- Jetson 1대 중심 시연

이 조건에서는 MQTT를 새로 도입하면 메시지 브로커, topic 설계, 장애 처리, 인증, 운영 문서까지 추가되어 시연 리스크가 커진다.

따라서 적용 판단은 다음과 같다.

- 2026-06-04 전: REST 유지
- 문서상 확장안: MQTT 후보로 기록
- 실제 도입 조건: 버스/정류장/Jetson 노드가 여러 대로 늘어날 때

### 4.5 watchdog 설정이 현재 기술 스택과 불일치한다

`hardware/watchdog_jetson.sh`는 현재 `MODEL="yolov8n.engine"`으로 되어 있다. 반면 README, `hardware/README.md`, `counter.py`는 YOLOv11 기준이다.

이 파일은 시연 자동 복구에 직접 영향을 주므로, 실제 Jetson 배포 전에 `yolo11n.engine` 또는 fine-tuning 결과물인 `best.engine` 기준으로 맞춰야 한다.

## 5.2 P1: 5월 15일 이후 바로 이어서 할 일

### 1. YOLO 학습 데이터셋 구성

현재 `hardware/configs/bustago_person.yaml`은 다음 구조를 기대한다.

```yaml
path: datasets/bustago_person
train: images/train
val: images/val
test: images/test
names:
  0: person
```

따라서 실제 데이터셋은 다음처럼 구성해야 한다.

```text
datasets/bustago_person/
├── images/
│   ├── train/
│   ├── val/
│   └── test/        # 선택. 시간이 부족하면 val로 대체 가능
└── labels/
    ├── train/
    ├── val/
    └── test/        # 선택
```

회의 요구사항인 8:2 분리는 우선 다음 기준으로 적용한다.

| 구분 | 비율 | 용도 |
|---|---:|---|
| train | 80% | 학습 |
| val | 20% | 정확도 검증 |
| test | 선택 | 최종 발표용 독립 평가. 데이터가 충분할 때만 분리 |

주의:

- 데이터가 적은 상태에서 train/val/test를 모두 나누면 각 세트가 너무 작아진다.
- 발표 전 시간이 부족하면 8:2 train/val을 우선 적용하고, 현장 카운팅 평가는 별도 Ground Truth로 보완한다.

### 2. 데이터 수집 기준

데이터는 "공개 데이터"와 "자체 촬영 데이터"를 분리해서 관리해야 한다.

| 데이터 | 목적 | 주의 |
|---|---|---|
| 공개 person/crowd 데이터 | 일반 사람 탐지 성능 보강 | 라이선스와 출처 기록 필요 |
| 자체 촬영 데이터 | 광주대 정류장 환경 적응 | 촬영 동의/삭제 절차 필요 |
| 시연 환경 영상 | 카메라 각도와 라인 튜닝 | 얼굴 비식별 또는 내부 검증용으로 제한 |

자체 데이터는 다음 조건을 나눠 촬영해야 한다.

- 밝은 실내
- 어두운 실내
- 역광
- 1명 통과
- 2명 이상 동시 통과
- 정지 대기 인원
- 빠르게 지나가는 사람
- 카메라와 가까운 사람
- 카메라 가장자리 사람

### 3. 데이터 증강 적용

회의에서 언급된 회전, 반전 외에도 다음 증강을 검토한다.

| 증강 | 목적 | 주의 |
|---|---|---|
| 좌우 반전 | 방향 변화 대응 | 라인 카운팅 의미와 혼동되지 않게 detection 학습에만 적용 |
| 밝기/대비 변화 | 조도 변화 대응 | 과도한 증강은 실제 영상과 멀어짐 |
| 약한 회전 | 카메라 각도 오차 대응 | 사람 bbox가 잘리는 수준은 제외 |
| blur/noise | 카메라 흔들림 대응 | 과하면 오탐 증가 |

Ultralytics YOLO 학습에는 기본 증강이 포함되므로, 별도 증강을 추가할 경우 어떤 증강을 썼는지 리포트에 기록해야 한다.

### 4. 학습 실행과 모델 산출물

현재 학습 entrypoint:

```bash
python hardware/train_yolo.py --epochs 100 --imgsz 960 --batch 16 --device 0
```

예상 산출물:

```text
runs/bustago/yolo11-person/
├── weights/
│   ├── best.pt
│   └── last.pt
├── results.csv
├── results.png
├── confusion_matrix.png
└── PR_curve.png
```

Jetson 배포 전에는 TensorRT 변환이 필요하다.

```bash
yolo export model=runs/bustago/yolo11-person/weights/best.pt format=engine half=True
```

배포 모델명은 발표와 문서에서 명확히 해야 한다.

추천 명명:

- baseline: `yolo11n.pt`
- fine-tuned: `bustago-person-best.pt`
- Jetson 배포: `bustago-person-best.engine`

### 5. 정확도 리포트 작성

## 5.3 P2: 발표 완성도를 높이는 일

### 1. 교통약자 기능을 발표 메시지에 반영

현재 학생 화면에는 저상버스 태그가 있다. 이를 발표에서는 단순 기능이 아니라 서비스 가치로 설명해야 한다.

적용 문구:

> BUSTAGO는 단순히 혼잡도를 보여주는 서비스가 아니라, 저상버스 정보를 함께 제공해 이동 약자의 탑승 판단을 돕는 정류장 정보 서비스로 확장할 수 있다.

보완 대상:

- `docs/발표자료/발표_슬라이드_구조.md`
- `docs/_회의준비/API_비교_설명가이드.md`
- 학생 PWA 시연 멘트

### 2. MQTT는 "확장 계획"으로만 제시

현재 구현에 MQTT를 넣는 것은 일정상 위험하다. 대신 발표 Q&A에서 다음처럼 설명한다.

> 현재 시연 범위는 정류장 1곳이므로 Flask REST 방식이 단순하고 검증 가능하다. 다만 부산대 사례처럼 버스·정류장·카메라 노드가 다수로 늘어나면 MQTT 기반 publish/subscribe 구조로 전환할 계획이다.

필요 문서:

- `docs/02_설계/MQTT_확장_검토.md` 또는 아키텍처 문서 내 확장 절

포함할 내용:

- 현재 REST 구조
- MQTT 전환 조건
- topic 예시: `bustago/stations/{station_id}/crowd`
- 장점: 느슨한 결합, 다수 구독자, 확장성
- 단점: broker 운영, 인증, 장애 대응 복잡도

### 3. 시연 성공 기준을 실제 측정값으로 갱신

`docs/03_구축/시연_계획서.md`는 AI 카운팅 정확도 목표를 "오차 ±2명 이내"로 적고 있다. 이 기준은 좋은 목표지만, 실제 측정 전에는 확정 성능처럼 말하면 위험하다.

적용 방안:

- 시연 전: 목표 기준으로 유지
- 측정 후: 실제 평균 오차율과 최대 오차를 함께 기록
- 목표 미달 시: 실패 조건과 개선 계획을 발표 자료에 투명하게 표시

## 9. 발표에서 사용할 판단 문장

### YOLO 학습 관련

나쁜 설명:

> YOLOv11을 학습했습니다.

좋은 설명:

> 기본 YOLOv11n 모델을 먼저 baseline으로 검증하고, 광주대 정류장 환경에서 촬영한 데이터를 8:2로 나눠 fine-tuning했습니다. 이후 baseline 대비 detection 성능과 실제 카운팅 오차율을 비교했습니다.

단, 실제 수치가 없으면 위 문장을 쓰면 안 된다. 수치 확보 전에는 다음처럼 말해야 한다.

> 현재는 YOLOv11 기반 추론 파이프라인을 구축했고, 현장 데이터 학습과 정확도 측정은 하드웨어 수령 후 진행 중입니다.

### MQTT 관련

나쁜 설명:

> MQTT도 적용할 수 있습니다.

좋은 설명:

> 현재 시연 범위는 정류장 1곳이라 REST POST 방식이 단순하고 검증 가능합니다. 정류장과 Jetson 노드가 늘어나는 단계에서는 부산대 사례처럼 MQTT publish/subscribe 구조를 도입해 데이터 생산자와 소비자를 분리할 계획입니다.

### 개인정보 관련

나쁜 설명:

> 촬영은 그냥 시연용입니다.

좋은 설명:

> 시연 전 촬영 안내와 동의 절차를 마련하고, 거부자 영상은 저장하지 않거나 요청 즉시 삭제합니다. 발표 자료에는 얼굴 식별이 가능한 원본 영상을 사용하지 않고 비식별 처리된 화면만 사용합니다.

## 11. 최종 권고

이번 회의의 핵심은 "기능을 더 추가하라"가 아니라 **이미 만든 시스템이 실제 환경에서 동작하고, 그 성능을 수치로 증명하라**는 것이다.

따라서 당장 MQTT나 새로운 기능을 구현하기보다 다음 세 가지에 집중해야 한다.

1. Jetson 카메라 카운팅이 실제로 backend와 frontend까지 이어지는지 증명한다.
2. YOLOv11 baseline, fine-tuning, 증강 결과를 수치로 비교한다.
3. 촬영 동의와 삭제 절차를 문서화해 개인정보 질문에 즉시 답할 수 있게 한다.

이 세 가지가 정리되면 프로젝트는 "데모가 되는 시스템"에서 "질문을 받아도 방어 가능한 산출물"로 올라간다.
